## Контракт для участника 3

Новый модуль `src/lib/proposals.ts` содержит чистые функции:

- `changeProposalStatus(proposal, status)` возвращает новую заявку после ручного решения бизнеса. До подтверждения этапа решения можно менять. Accept сам по себе не начисляет баллы.
- `confirmProposalProgress(proposal, evidence, confirmedAt?)` работает только для ACCEPTED и непустого свидетельства. Возвращает заявку с одним подтверждённым этапом и ровно 10 баллами. Повторный вызов сохраняет первоначальные свидетельство, время и баллы.
- `canChangeProposalStatus(proposal)` возвращает false после подтверждения этапа. Используйте для скрытия или отключения Accept/Reject.

После подтверждения этапа смена статуса на REJECTED или PENDING вызывает ошибку. Повторное присвоение ACCEPTED допустимо и не начисляет баллы. Подтверждённый этап нельзя удалить, переписать или перенести на другую команду/задачу. Явный Reset demo data начинает демонстрацию заново.

В обработчиках `App.tsx` замените прямое изменение `status` и `progress` вызовами этих функций. Обрабатывайте ошибки до изменения React-состояния и показывайте сообщение пользователю. Это подключение относится к участнику 3 и ещё не сделано: нынешний обработчик может временно показать REJECTED в памяти React, хотя сохранение такого изменения уже блокируется.

## Хранилище

Ключи localStorage сохранены: `aisana.tasks.v1` и `aisana.proposals.v1`.

- Проверяются структура, непустые ID, уникальность ID внутри списка, ISO-время, статусы, HTTP(S)-ссылки и инварианты прогресса.
- Пустые списки и задачи с нулевым рейтингом допустимы. Проверка хранения не вводит порог публикации или отклика.
- Неизвестные поля отбрасываются. Сохранённые `score`, `rating` и `breakdown` не используются: оценка вычисляется из описания.
- При повреждении показывается независимая копия демонстрационного набора и предупреждение. Исходный повреждённый JSON не перезаписывается при чтении.
- Ошибка записи сохраняет допустимые изменения в памяти текущей страницы; повторный load возвращает их. Перезагрузка страницы при неработающем localStorage эти изменения теряет.
- Успешная операция с одним набором не скрывает предупреждение другого набора.
- Reset возвращает независимые копии исходных данных.

`saveTasks` и `saveProposals` возвращают true только при успешной записи в localStorage. False означает отказ валидации либо недоступное хранилище; причину содержит `storageWarning`. После отказа валидации предыдущие данные остаются неизменны. После ошибки записи `loadTasks` / `loadProposals` возвращают принятую копию из памяти. UI может восстановить согласованное состояние вызовом load; текст ошибки следует прочитать до этого вызова, поскольку успешное чтение очищает предупреждение соответствующего набора.

Слой хранения проверяет сохранённый ранее прогресс даже при обходе функций переходов. Это защита от ошибок приложения, не авторизация: редактирование localStorage через DevTools и параллельные вкладки не являются защищённой средой. Ссылочная целостность между раздельными наборами задач/команд/заявок пока не обеспечивается транзакцией.

## AI и рейтинг

`createAiAdapter()` совместим с текущими вызовами. Дополнительно доступны параметры `{ endpoint, fetcher, timeoutMs }` для проверок. В приложении сохраняется таймаут 8000 мс и настройка `VITE_TASK_DOCTOR_ENDPOINT`.

После запроса `adapter.getDiagnostics()` возвращает:

```ts
{ mode: 'offline' | 'live', reason:
  'not-configured' | 'not-called' | 'success' | 'http' |
  'invalid-response' | 'timeout' | 'network' }
```

Участники 2/3 могут показать Offline AI и причину fallback. Диагностика относится к последнему завершённому запросу данного адаптера.

Внешний сервис получает только описательные поля карточки и `AI_PROMPT`. Ответ должен содержать минимум три непустых вопроса по разным разрешённым полям. Некорректный ответ, повтор поля, HTTP/JSON/сетевые ошибки и таймаут запроса или чтения ответа включают локальные вопросы. Дополнительные поля ответа не применяются к карточке. В карточку копируются только строковые ответы человека; ID, публикация, дата, score и другие метаданные через вопросы не меняются.

`FIELD_MIN_LENGTH` и `isFieldComplete` в `scoring.ts` используются также локальным Doctor: пороги оценки и вопросы согласованы. Веса и прежние пороги длины не изменены. Рейтинг остаётся эвристикой полноты текста, а не доказательством содержательного качества или истинности фактов. Ручное подтверждение публикации остаётся ответственностью рабочего процесса в App.

## Воспроизводимость и проверки

Прямые зависимости закреплены на точных версиях уже проверенного lockfile; транзитивные пакеты не обновлялись. Объявлен Node.js >=22.16.0, как в текущем README.

```sh
npm ci
npm test
npm run build
```

Тесты запускают реальные TypeScript-модули. Набор расширен с 5 до 22 тестов: 512 сочетаний полноты рейтинга, общие пороги Doctor, защита метаданных, некорректные AI-ответы, таймаут запроса и тела ответа, ручные решения, однократность и финальность +10, перезагрузка, повреждение данных, отказ чтения/записи, восстановление и неизменность seed-данных. Тесты AI используют подменённый транспорт; реальный внешний сервис не проверяется.

E2E-проверка браузера не входит в эту часть. После подключения функций участником 3 нужен прогон: Accept → evidence → +10 → попытка Reject → reload. Заявка должна остаться ACCEPTED, сумма — 10, кнопки смены решения — недоступны.

Фактическая проверка этой ветки: `npm ci --offline --no-audit --no-fund` из локального кэша, затем `npm test` (22/22) и `npm run build` — успешно. Dev-сервер на `http://127.0.0.1:5173/` отвечает HTTP 200 и отдаёт новый доменный модуль. Это не заменяет браузерный E2E-прогон.
